# Тестовое задание

Нужно ускорить ночную синхронизацию сущностей из CRM в Postgres.
Точка входа — `collect_leads_customers(is_full=True)`.
Нагрузка: 20 тыс. покупателей и 50 тыс. сделок.
Сейчас прогон делает отдельный запрос и commit на каждую сущность
и в конце ещё раз читает всю таблицу.
## Некоторые правила бизнес-логики
- Покупатель без логина пропускается.
- Покупатель ищется по id покупателя в CRM, иначе по логину среди уже сохранённых сделок.
  Если по логину нашлось больше одной записи, совпадение не используется.
- Сделка ищется по id сделки в CRM, иначе по логину среди покупателей.
  Если это две разные записи, они сливаются в ту, что нашли по сделке; вторая удаляется.
  Если не нашлось ничего, создаётся новая запись.
- После успешного полного прохода удаляются покупатели и вложенные
  сущности, которых не было в этой выгрузке, в том числе с «удалить» в имени.
- Если сбор прервался, удаление не запускается.
Падения и расхождения кода с этим списком нужно поправить.
Формат JSON в полях можно сохранить.
## Ограничения
- Python >= 3.9, Flask, SQLAlchemy, PostgreSQL.
- Celery, брокер и боевой API поднимать не нужно.
- Новые сервисы не добавлять. Схему хранения можно менять.
- Ночной прогон ищет покупателя и сделку по id CRM и по логину.
  Другие части системы ищут покупателя или сделку по точному логину и по названию.
  этот поиск писать не нужно, но выбранная схема должна его выдерживать.
  Также нужно поддерживать связь сделка-покупатель.
- Способ реализации на ваше усмотрение, правила выше обязательны.
Полный объём локально гонять не нужно: клиента CRM в репозитории нет.
Оцените память процесса и число запросов к Postgres на указанных цифрах.
## Результат
Ссылка на репозиторий и короткий README:
что было дорого, что изменено, что оставлено и почему.

## Решение

### Что было дорого

Оценка по коду для 20 тыс. покупателей и 50 тыс. сделок:

- На каждую сущность шло 1–2 поиска `@>` по JSONB без индекса. Всего около 120 тыс. полных
  сканов таблицы с распаковкой JSON, поэтому время росло квадратично.
- Около 250 тыс. запросов и 70 тыс. commit только на сбор.
- Чистка читала всю таблицу в ORM-объекты, а это порядка 200 МБ JSON и примерно 1 ГБ в Python.
  Потом шло ещё около 70 тыс. UPDATE и commit, по одному на элемент массива.
- Ночью переписывалась каждая запись, даже если в CRM ничего не менялось.

### Что изменено

Покупатели и сделки переехали из JSONB-массивов в таблицы `amo_customer` и `amo_lead`, по строке
на сущность. Первичный ключ — id в CRM.

- **Формат JSON:** элемент массива лежит в `data` без изменений.
- **Связь сделка-покупатель:** общий `abstract_customer_id`. Слияние — это один UPDATE строк, без
  пересборки JSON.
- **Внешний поиск:** `login` и `name` вычисляются из `data` и не могут с ним разойтись. На `login`
  стоит btree, на `name` — GIN pg_trgm для `LIKE`, `ILIKE` и `=` (миграция 002).

Прогон в `CustomerSync`:

1. В память читается проекция таблиц без JSON: id, запись, логин, хеш.
2. Все решения принимаются по этим индексам, поэтому каждая следующая сущность видит результат
   предыдущей.
3. В базу уходит только то, чей хеш изменился: upsert пачками по 500, каждая пачка — транзакция.
4. Чистка — 5 запросов в одной транзакции, Python не читает JSON из таблицы.

### Оценка

Замер `tests/bench_sync.py`: синтетическая выгрузка 20/50 тыс., `api_value` около 3 КБ,
встроенный PostgreSQL 16 на Windows, без сети и задержек CRM.

| Сценарий | Запросов | Commit | Время | Пик RSS |
|---|---:|---:|---:|---:|
| Пустая база, все записи новые | 207 | 162 | 22 с | 124 МБ |
| Ничего не изменилось | 7 | 2 | 3,5 с | 130 МБ |
| 5 % изменилось, 1 % исчез | 15 | 10 | 4,7 с | 138 МБ |

- **Память:** 75 МБ занимает сам процесс до прогона, пик Python-кучи — около 40 МБ. Индексы от
  размера JSON не зависят. От него зависят только страница CRM (250 объектов) и пачка (500 строк).
- **Запросы:** без изменений их всегда 7. С изменениями добавляется примерно по запросу на
  500 строк и до пяти на пачку со слиянием. Первый прогон после миграции перепишет все строки,
  потому что хешей ещё нет: это около 150 запросов.
- **Время в бою** теперь определяет CRM: минимум 280 страниц с паузой 1 с, то есть от 5 минут.

### Падения и расхождения с правилами

Исправлено в сборе и чистке:

- Новые покупатели попадали в `ids_map[None]`: `id` ещё не был выдан, а `NOT IN (NULL, ...)` не
  удалял ничего.
- Слияние возвращало `None`: падение, сделка не записывалась, её id и id второй записи терялись
  для чистки. `send_methods` при слиянии пропадали.
- Ошибка на одной сделке проглатывалась, и чистка всё равно шла по неполным данным. Сбой самой
  чистки тоже проглатывался.
- `filter_merge_abstract_customer` проверял `l` вместо `c`: один плохой элемент стирал весь
  массив. Падал на `name = None`, делал commit на каждый элемент.

Исправлено в клиенте и JSON:

- `Lead` не читал контакты из `_embedded`, поэтому контакты сделок удалялись как отсутствующие.
- `get_field` падал на `custom_fields_values = null`, который API возвращает для сущности без
  полей.
- Клиент падал с `KeyError`, если последняя страница была полной и без `next`. Короткая страница
  с `next` считалась концом, и обрезанная выгрузка выглядела полной. Теперь конец определяется
  только по `next`.
- `is_robot` и `is_nds` были `True` при значении поля `False`.
- В `amocrm.py` не было `get_schema` и `as_dict`. Добавлены минимальные версии без новых
  зависимостей. Если настоящий клиент живёт в другом месте, из этого файла нужны только правки
  выше.
- В `requirements.txt` не хватало `requests` и драйвера, а зафиксированные версии не ставились на
  Python 3.9. Добавлены маркеры версий.

### Решения, которые стоит проверить

- **Покупатель без логина** не пишется, но и не удаляется: он был в выгрузке. Раньше чистка его
  удаляла.
- **«Удалить» в имени** удаляется, даже если сущность есть в выгрузке, как и задумано в старом
  коде. Контакт, на который ссылалась только такая сущность, уходит вместе с ней.
- **Контакты сверяются в пределах записи:** контакт остаётся, только если на него ссылается
  покупатель или сделка этой же записи, как в старом `ids_map`. Компании сделок тоже считаются,
  раньше они игнорировались.
- **Сбой на одной сущности** не останавливает прогон: остальные данные сохраняются, чистка
  пропускается.
- **Пустая выгрузка** при непустой таблице считается сбоем, чистка не запускается. Этого правила
  нет в списке, я добавил его как защиту от стирания всей таблицы.
- **Сделка без логина и совпадений** создаёт запись по правилу из списка. Старый docstring
  говорил «пропускаем», но код тоже создавал запись.
- **Неоднозначный логин у сделки** не используется, как у покупателя. В правилах это сказано
  только про покупателя, но старый код делал так же.

### Что оставлено и почему

- `amo_contacts`, `amo_companies`, `send_methods` остаются JSONB: их пишет не этот код, и формат
  для тех писателей менять незачем.
- Устаревшие покупатели и сделки участвуют в поиске до чистки, как и раньше: в том числе
  считаются при проверке логина на неоднозначность.
- Пауза 1 с между страницами CRM оставлена как защита от лимитов API.
- Защиты от двух одновременных прогонов нет, как и раньше.
- Символ `\u0000` в данных CRM уронит всю пачку: JSONB его не хранит. Прогон остановится без
  удаления, а эта пачка и всё после неё не запишутся, пока данные не исправят.

### Запуск

Порядок выката:

1. Сделать бэкап и остановить ночную задачу.
2. Применить `migrations/001_split_customers_and_leads.sql`, затем `002_name_search_indexes.sql`.
3. Перевести внешний код с JSONB-колонок. Чтение `record.amo_customers` и `record.amo_leads`
   через ORM работает как раньше, но это свойства: фильтры `@>` по ним и прямой SQL нужно
   переписать на новые таблицы.
4. После проверки первого прогона применить `003_drop_legacy_json.sql`.

Драйвер нужно указывать явно: `postgresql+psycopg2://...`. В SQLAlchemy 2.1 схема
`postgresql://` по умолчанию ведёт на psycopg 3, которого нет в зависимостях.

Тесты нужны настоящий Postgres, база очищается перед каждым тестом:

```bash
pip install pytest
```

```bash
TEST_DATABASE_URL=postgresql+psycopg2://user:pass@localhost/test pytest tests
```
